# Bounded application inputs

The application accepts useful showcase edits through named, bounded receivers while retaining the current visual experience and ordinary Node/PostgreSQL path. This assessment follows the current inputs through their runtime owners. Synthetic records and selectable showcase roles remain distinct from future verified identity.

The 2026-11-17 follow-up supersedes the earlier conclusion that the delivered input controls completed the bounded input assessment: per-request bounds were present, while parallel requests could still start an unbounded amount of work. The focused follow-up adds shared admission across both GraphQL routes. The earlier text, command, cohort and document-policy findings remain accepted.

## Shared request admission

`server/security/request-admission.mjs` owns one in-flight counter. `scripts/serve.mjs` passes the same owner to the read API and visitor workspace API. Eight requests can be active; an excess request receives **503 Service Unavailable**, a one-second `Retry-After` hint, `Cache-Control: no-store` and a bounded GraphQL error. The owner keeps no queue, client identifiers, request bodies or token map. Eight is an initial conservative showcase budget, not a measured hosting throughput claim; the named constant provides the tuning point if observed use warrants it.

Each API registers admission inside its deadline wrapper and outside its owned handler/cleanup. A deadline can return a timely response while underlying work is still finishing; the slot remains occupied until that work settles. Success and failure release their slot in `finally`. Existing connection cancellation and transaction deadlines retain their separate roles.

The Source client already treats temporary HTTP failure as an unconfirmed request, retains the draft and retries with the same command identity. Read clients retain their existing retry path. Static files remain available independently of this API budget. This process-local boundary controls concurrent application work; it does not provide per-person fairness or provider-wide denial-of-service protection. Hosting-level traffic controls belong to the deployment receiver, especially if the app gains multiple processes or verified accounts.

## Production document policy

`server/security/document-policy.mjs` derives the CSP once at startup from `dist/index.html`. It recognizes the trusted `initial-load-bootstrap` and stops startup for review if another inline script appears. Hash bytes include the script's exact whitespace. Same-origin assets and requests remain allowed; Google Fonts retains its two stylesheet/font origins. Inline styles remain necessary for the current React geometry, camera transforms, theme variables and motion.

The policy disables plugin objects, document base changes and child frames, and confines form targets to the same origin. Parent embedding remains available: a deployment-specific parent-origin policy has not been established. Any future `frame-ancestors` or `X-Frame-Options` decision needs a preview and published-hosting check. The production document receives the policy; the explicit local GraphQL explorer retains its separate development route.

The trusted build owns executable assets. This fitted policy establishes the named restrictions, rather than general safety of all same-origin code or future inputs. Ordinary startup computes it from the document it serves.

These observations use controlled handlers for concurrency; the follow-up requires no hosted database access or schema changes.

## Research decision

The reassessment compared keeping the existing request limits, adding generic query-cost/depth middleware, adding a client/IP rate limiter, and bounding concurrent application work. The fixed operation allowlist already controls query shape. A shared in-flight owner directly addresses the observed connection pressure with a small, dependency-free implementation. Client identity and trusted proxy attribution are not assumed; a verified-identity or hosting-scale change can reopen per-client/distributed rate limiting.

Official sources checked on 2026-11-17:

- [GraphQL security and demand control](https://graphql.org/learn/security/) distinguishes trusted documents, pagination, batching and runtime demand controls. This supports retaining the reviewed document set and adding a separate resource boundary.
- [OWASP GraphQL guidance](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html) joins input validation, authorization, timeouts and resource controls. The recommendation here applies those layers to the application's actual receivers.
- [Yoga persisted operations](https://the-guild.dev/graphql/yoga-server/docs/features/persisted-operations) documents explicit arbitrary-operation admission. Production retains the reviewed registry; the local explorer remains separate.
- [MDN 503 Service Unavailable](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/503) distinguishes temporary server overload from client-specific rate limiting and describes retry/caching considerations. The overload response follows that distinction.
- MDN's [CSP guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP) and [script-source reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src) support exact script hashes and event listeners. Its [frame-ancestors reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors) distinguishes parent embedding from child-frame loading.
