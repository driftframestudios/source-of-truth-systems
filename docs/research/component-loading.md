# Local feedback for primary panels

Visitors should see which record they selected immediately, understand genuine waits in that record's panel, and keep exploring the surrounding scene. The recommended first repair keeps the Sample history tray present while its decorative thread and reveal run, then places real history-request feedback beside the selected record. A restrained geometric placeholder is useful when a primary panel has no usable content; it should dissolve as content becomes ready.

**Status:** research supporting the selected-history loading experience. The first focused repair is recorded in the [loading contract](../loading-experience.md): continuous tray, parallel reveal, keyed primary source strip and real-request geometric activity. This supersedes the proposal-only status; the audit below preserves the observed pre-repair mechanism. A full geometric skeleton remains conditional on a future panel lacking usable content. The earlier source audit and production timing observation used the same loading and Plate owners. Those historical observations explain the decision; the [loading contract](../loading-experience.md) names the current owners and receiving checks. React is pinned to 18.3.1; the existing Motion library, typed themes and CSS composition are sufficient.

### Observed Sample history delay

A production Chromium probe selected Sample history, waited for the tray, then hovered C3 without pinning or requesting history. It observed **zero GraphQL requests**. In one settled desktop run, the tray mounted after roughly **0.89s**, became opaque around **1.10s**, record DOM appeared around **0.21s** after hover, the header began showing readable ink around **0.82s**, and the clip opened fully around **1.26s**. These are local observations, not cross-device performance claims or acceptance thresholds.

Source explains the sequence: 90ms hover intent; summary/record exit of 100–120ms; `THREAD_DRAW_S = 0.46`; body start at thread time + 0.1s; a 0.5s clipped reveal and staggered children. The camera has its own 130ms wind-up and spring completion. This establishes a material animation-origin delay even when records are available. It leaves real hosted latency and low-end-device rendering cost open for their own observations.

## Four treatments and their fit

| Option | Useful property | Cost or boundary | Decision |
| --- | --- | --- | --- |
| Progress bar | Familiar place to track a bounded operation; an indeterminate line can signal activity with little space. | The current fetch supplies no fraction or bytes-complete denominator. A global bar would misrepresent a local request. | Reserve determinate progress for measurable work. Use an indeterminate rail only if it reads better than the small local indicator in the panel. |
| Small throbber with a short label | Names a specific pending request without displacing working content. | Repeated spinners compete with the 3D scene and imply that local selectors need processing. | Preferred for background checking beside existing content: “Checking C3 history…” in one scoped status rail. |
| Shape-matched skeleton | Reserves a primary panel's footprint and previews its hierarchy. | A dense copy of every row creates noise; showing it over useful data adds churn. Exact response shape may vary. | Use only when the primary receiving panel lacks usable content: heading strip and a few broad content blocks. |
| Restrained geometric/Mondrian panel, then dissolve | Connects the existing loading art to the panel's structure using a few theme-colored rectangles. | Decorative novelty is a design hypothesis; it has no established advantage over a conventional skeleton here. Random blocks can imply an error or hide the expected content structure. | Synthesize with the skeleton: stable, panel-shaped regions, low contrast, one subtle movement, short nonblocking exit. Keep it exclusive to primary-panel waits. |

The recommended combination is **immediate stable structure + one local request receipt + a geometric skeleton only for truly absent content**. It draws on the existing plate loading vocabulary without replaying the full startup composition for every selection. Existing results remain readable while a source is checked. Once content is ready, a proposed 150–200ms opacity dissolve may accompany its first paint; that duration is a design trial, not a forced wait or research-derived threshold. Reduced motion shows the ready content directly. Fast/cache hits earn no additional ceremony.

## State and ownership contract

Keep request identity separate from animation identity. A selected read carries the current permission-scope key, plate ID, well ID and request attempt. The [cache owner](../../src/app/services/plateHistory/cache.ts) partitions successful histories by scope, then keys each history by plate and well. A scope change cancels obsolete requests and selects its own permitted projection; denied or missing records cannot reuse another scope’s history. A future change to source or dataset version must also enter identity and invalidation before reuse. The permission scenario chooser remains demonstration policy rather than server authentication.

The request owner projects idle/loading/ready/unavailable activity, while its current scope and blocked-read results govern denial and missing records. Keep these policy outcomes distinct from transport failures. Ready contains source, results and missing metadata; empty/missing are meaningful ready outcomes rather than extra independent flags. The panel receives a typed projection of this state, the requested identity and a Retry command. Rendering never owns the request or a duplicate data cache.

- **Selection:** publish the chosen identity immediately. Cancel the preceding request and only accept the current attempt. The current request helper already supplies the essential lifetime guard.
- **Pending with useful content:** retain correctly identified examples or same-key cached data with explicit source. A previous well's record must retain its old identity until replaced; it must never silently acquire the new well label.
- **Pending without useful content:** reserve the panel's geometry, show its heading and geometric skeleton, and keep scene navigation available.
- **Cache hit:** publish ready directly. A spinner caused by an effect-only cache lookup is avoidable churn; establish one keyed ready projection rather than introducing a minimum display duration.
- **Failure/deadline:** settle to a local unavailable receipt with Retry; retain explicitly identified examples where policy permits them. Retry belongs to the current key. Raw transport/database detail stays out of visitor copy.
- **Denied:** show the actionable permission outcome from its policy owner. An error-shaped network failure cannot establish denial. The current read policy already governs cached and example fallback visibility; a denied result stays withheld from the receiving projection.
- **Cancellation:** abandoned selection or hidden/unmounted view stops outstanding work and visual timers silently. A subsequent selection owns its own state. The current deadline remains a recovery boundary, not a progress denominator.
- **Ready:** make content available immediately. Any decorative exit uses a separate, short, cancellable reveal lifecycle and never gates interaction or data publication.

**Supersession:** The later [shared accepted-state and scoped-cache owners](../workspace-audit.md) now retain records across responsive workspaces. The keyed request approach remains proportionate to the app. Add a query library or external-store subscription when concurrent subscribers, invalidation or real server mutations make that cost worthwhile; a second cache beside the current one would obscure ownership.

## First focused repair and evidence

1. **Make the tray continuous.** Reserve its current geometry when Sample history is requested; show the selected identity or existing summary while the camera swings. Keep the camera spring, thread, ink hierarchy and dark/light/contrast palettes. Update result identity/content promptly and run the thread/reveal decoration in parallel. An available record should not spend the full thread + clip + child sequence invisible.
2. **Connect the actual request.** Pass a selected-history status projection from `LanesView` and `MobilePlate` into the primary record companion. When hover previews a different well, continue identifying that local example rather than attaching the pinned well's request label. Give the one visible request receipt and Retry a clear owner, avoiding duplicate live announcements with `PlateHistorySource`.
3. **Add only the missing placeholder.** A small shared loading visual accepts an explicit mode and label; it has no fetch, timer-based progress or business logic. Use its geometric skeleton only for an empty primary panel, and its small inline state when content is already useful. Preserve the existing initial workspace loading treatment.
4. **Prove the boundary.** Extend existing request tests for replacement/cancellation/deadline where needed. Browser journeys hold an actual history response, select another well, release responses in reverse order, retry a failure, revisit cache and exercise ready-empty/missing. Observe identity, readable status and terminal state. Test local hover with zero reads, rapid record changes, theme modes, reduced motion and mobile companion geometry. Preserve startup payload/deployment checks if shared imports change.

A local production timing probe already establishes the animation-origin delay; its cycle-scoped script and raw output remain ignored local artifacts. Existing `tests/browser/plate-history.spec.mjs`, `loading.spec.mjs` and Plate journeys provide the durable test owners. The repair should add only the assertions needed to distinguish truthful waiting and prompt record selection. Extensive performance instrumentation, dependency replacement, global loading overlays and a redesign of unrelated panels remain outside this first tranche; a measured residual delay can reopen the appropriate owner afterward.
