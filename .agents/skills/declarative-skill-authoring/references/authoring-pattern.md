# Authoring pattern

Use this pattern during creation or structural revision. Retain sections that change a reader's decisions; the outline is a writing aid rather than a schema requiring identical length across skills.

```markdown
---
name: capability-name
description: <Third-person method and result>. Applies when <specific triggering conditions>.
---

# Capability name

## Contract
- **What:** <bounded job>
- **When:** <activation conditions>
- **Boundaries:** <current authority, scope and transfer limits>
- **Result:** <observable receiving state>

## Fit and attention
<Useful and poor-fit cases, smallest useful dose, relevant peer owners,
the method's blind spots, and the condition that releases the work.>

## Inputs, defaults and output
<Minimum current evidence, source owners, missing-input response,
ordinary route and exact receiving artifact or behavior.>

## Rules
### Rule: <consequential invariant>
<The distinction that changes a decision, its source and its consequence.>

## Operating sequence
<Ordered actions only where order changes correctness or recovery.>

## Conditional context
<Direct local link and exact load condition for each optional reference.>

## Recovery and completion
<Retained state, smallest workable recovery, observed completion,
open evidence boundary and material event that reopens the task.>
```

Examples belong beside the decision they clarify or in a short scenario section. Write Given/When/Then only when those branches help interpretation. Mark intended examples separately from executed cases. Cite current source when a source-specific rule matters; keep long receiver inventories in a conditional reference when they compete with the core procedure.

## Runbook companion

A runbook orders a known multi-phase route across current owners. Its short header carries `title`, semantic `version`, `status`, `audience`, `source_band` and singular `task_type`. Use `working`, `exercised`, `stable` or `retired` to describe observed maturity. One completed exercise can establish `exercised`; repeated settled use supports `stable`.

Name the receiving state, entry conditions, authorized action mode, ordered phases, checkpoint meaning, recovery and stop condition. An unavailable entry condition receives a safe next action. Issues retain current scope and acceptance, while user instructions retain authority. A public-possible return includes the changed artifact, normalized evidence, coverage and next receiver; raw logs, credentials and private locators remain with their existing protected owner.

The [runbook index](../../../../docs/runbooks/README.md) shows current local examples. A first authoring exercise checks whether another reader can enter and finish from the runbook and linked source, rather than treating the header as proof of readiness.

## Proportionate review

- **Routing:** A realistic task selects the skill, and a plausible near miss selects direct work or a different owner.
- **Structure:** Metadata names a capability; links resolve; all required context travels with a clone.
- **Action:** The reader identifies actual actors, current source, authority and a bounded output.
- **Evidence:** An authored example, executable test, review and hosted observation retain distinct meaning.
- **Recovery:** A consequential failure preserves useful state and identifies a next action.

Use an independent reader for complex methods when available. Supply the task and raw evidence without the intended answer. Keep the exercise within existing authorization and record its actual result, including any remaining gap. A runtime suite becomes relevant only when executable behavior or its check owner changes.
