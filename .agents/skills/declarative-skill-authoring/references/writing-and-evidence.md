# Writing instructions another collaborator can use

This local guide applies to skills, runbooks and their receiving summaries. It combines the exemplars' [supportive-change register](https://github.com/driftframestudios/human-ai-systems-exemplars/blob/main/.agents/skills/supportive-change-writing/SKILL.md) and [agency-and-action method](https://github.com/driftframestudios/human-ai-systems-exemplars/blob/main/.agents/skills/agency-and-action-writing/SKILL.md). Those public contracts preserve the deeper source lineage; the operative method is included here for independent clones.

## Lead with a useful state

Name what the reader can create or verify. Use concrete actors, verbs and objects when supported: “The command owner resolves current consent before accepting a restore.” Professional distance, an impersonal construction or a precise abstraction remain appropriate when the actor is unknown, protected or irrelevant. Preserve contribution boundaries; participation and ownership make different claims.

Give each paragraph one job. Connect the action to its material consequence, such as retaining a draft or releasing a database connection. Warm, direct language treats strain as a condition of the workflow and gives the reader a workable next move.

## Classify negation before revision

| Language function | Treatment | Receiving check |
| --- | --- | --- |
| Generative instruction or tone goal | State the desired behavior directly when it preserves meaning. | Does a representative receiving task produce the intended behavior? |
| Safety, privacy, compatibility or authority boundary | Preserve the exact exclusion beside its permitted route. | Can the reader identify the boundary and useful continuation together? |
| Definition or evidence limit | Preserve the qualifier beside the supported claim. | Does the revised claim retain the original scope? |
| Test assertion or absent-state check | Preserve executable semantics and name the invariant. | Does the same plausible fault still fail? |
| Source title, quotation, governed label or code identifier | Retain exact source fidelity. | Does the carrier still match its source? |

This is an authoring heuristic, not a claim that every model handles negation alike. Prompt following, training-time learning, retrieval and multilingual interpretation are different observations. Test a consequential rewrite in its actual receiver. Ordinary prose edits generally need a proportionate editorial review.

Keep a boundary in the same sentence, bullet or table row as the action it governs so partial context preserves their relationship. A positive operating target often reduces inference; a hard exclusion still deserves explicit language.

## Examples that retain meaning

| Source problem | Useful revision | Preserved boundary |
| --- | --- | --- |
| “Do not lose edits when resizing.” | “The shared accepted-state owner retains edits while the receiving layout remounts.” | The layout reads the existing owner; it cannot replace accepted work with defaults. |
| “No tests failed,” after runner output confirms 15 executed browser passes and no database execution. | “The selected 15 browser journeys passed. Database behavior remains unobserved in this run.” | A skipped or absent assertion establishes no adjacent behavior claim. With only a zero-failure count, report that count and inspect execution before claiming a pass. |
| “Don't print secrets.” | “The summary carries normalized results. Credentials and raw request headers remain with the protected runtime owner.” | Secret material never enters the published summary. |
| “The fix was made.” | “The command owner now rechecks scope when the visitor submits the edit.” | The claim covers that owner and acceptance event. |

## Review and return

1. Identify the audience, actor, action, affected object and supported consequence.
2. Revise only what the evidence establishes; keep missing facts as open questions with a receiving owner.
3. Classify retained negations and pair material exclusions with an affirmative continuation.
4. Distinguish verified source behavior, observed tests, supported inference, proposal and authored scenario.
5. Check headings, bullets, table cells, examples and code comments as well as paragraphs.
6. Return the changed state, what the observation establishes, its coverage boundary and the next revisable move.

One receiving record is enough. A PR body can carry the decision and evidence; linked runbooks carry the repeatable procedure. Reopen wording when an actual reader, source change or receiving result shows that it changes the wrong behavior.
